# CLI Architecture For Eidos

## Overview

CLI Эйдоса — диалоговый рантайм поверх `kernel/*`.

Цикл: `user_input → context_prep → LLM call → [multi-turn tools] → post_process → save → output`

## OpenCode и нативный CLI

- **Нативный CLI** сам является источником переписки: сообщения пользователя и ассистента пишутся в нашу память (рабочая память / сессия / при необходимости общий лог событий). Автоматический boot **не** обязан тянуть OpenCode при каждом запуске.
- **Адаптер OpenCode сохраняем** как опцию **импорта**: подтянуть уже прошедшую сессию из OpenCode и продолжить работу в своём CLI (миграция, восстановление истории). Команда вроде `sync-opencode` / `import-opencode` — явное действие пользователя, не дефолтный старт.

## Architecture

Пакет `cli/` + entrypoint `eidos.py`.

### Компоненты

| Модуль | Назначение |
|--------|-----------|
| `eidos.py` | Тонкий entrypoint |
| `cli/app.py` | CLI-команды: `chat`, `ask`, `run` (именованные пайплайны), `review`, `sleep`, `boot`, `import-opencode` |
| `cli/runtime.py` | Оркестратор полного цикла (EidosRuntime), синхронный в v1 |
| `cli/context.py` | Пайплайн сборки контекста для модели (не «ядро памяти», а оркестрация вызовов API памяти и инструментов) |
| `cli/agent_backends.py` | Контракт Agent Backend + реализация OpenAI-compatible HTTP по **имени профиля** из конфига |
| `cli/pipelines/` | Именованные оркестрации этапов: `research`, `experiment`, `code_review`, chat |
| `cli/llm.py` | Тонкая обёртка или слияние с `agent_backends` (избегать дублирования HTTP) |
| `cli/tools.py` | Инструменты + multi-turn цикл; выполнение через InstrumentalRegistry |
| `cli/postprocess.py` | Ethics, verifier, pulse suggestions (позже — как явные этапы пайплайна) |
| `cli/persistence.py` | Сохранение шагов, управление sleep |
| `cli/session.py` | Persistent session state между запусками |

### Multi-turn протокол (инструменты)

Явный цикл до финального текстового ответа:

1. Собранный контекст + история хода → запрос к модели.
2. Если в ответе есть tool_calls — выполнить инструменты, записать результаты в историю хода (роли `assistant` / `tool` или эквивалент согласно API).
3. Повторять шаги 1–2, пока модель не вернёт финальный ответ без инструментов или не сработает лимит итераций/токенов.
4. После завершения цикла — постобработка и запись в память.

Отдельно зафиксировать в коде: максимум раундов инструментов, таймауты, политика ошибок инструмента (ретрай vs сообщение модели).

### Рабочая память и контекст (концепция)

**Цель:** «рабочий контекст для модели» — это не просто последние *N* токенов непрерывного диалога, а **сборка под бюджет**:

- недавняя реплика диалога (сырой текст);
- при нехватке места — сжатые/суммаризированные более старые отрезки;
- активный план по текущей задаче (если есть);
- слоты внимания / cue-based подборки из эпизодической и семантической памяти;
- при необходимости — фрагменты внешней памяти, миссии, инструментальных трасс.

То есть **пайплайн подготовки контекста** вычисляет, сколько места осталось под «текущее действие» (очередной запрос пользователя + ответ + буфер под tools), и укладывает в этот бюджет слои из разных источников.

**Замечание по текущему ядру:** сегодня `WorkingMemory` в `kernel/memory.py` — это прежде всего JSON-сессия (`events`, `attention_slots`, …). Концепция выше может потребовать рефакторинга: отдельный **сборщик контекста** с токен-бюджетом и явными стадиями, не смешивая «хранилище событий» и «то, что уходит в промпт».

### Пайплайны памяти и ядро (направление развития)

- **`cli/context.py`** — один из **пайплайнов сборки**: вызывает не «память как монолит», а **стандартизированные API** каждого вида памяти (рабочая, эпизодическая, семантическая, внешняя, инструментальная, цели, …) с параметрами, подходящими именно этому режиму (лимиты, фильтры, режим ранжирования).
- В перспективе ядро: **единая хронологическая база событий** (весь текст: пользователь, ассистент, код, результаты инструментов) и поверх неё — специализированные «агенты»/слои памяти, которые индексируют, отбирают и готовят выборки под запрос пайплайна (простой случай: семантический + временной поиск по окну; сложнее: паттерны успешных вызовов инструментов для текущего процесса).
- Разные **режимы пайплайна**: пробуждение (boot), разработка, исследование, свободный чат, игровой режим — это разные композиции одних и тех же API памяти с разными весами и бюджетами.

**Обязательные именованные пайплайны (продуктовое требование):**

| Пайплайн | Назначение |
|----------|------------|
| **исследование (research)** | Обзор контекста и литературы, гипотезы, план проверки, связь с `experiments/` и episodic |
| **научный / инженерный эксперимент** | Протокол шага (что меняем, что измеряем), журнал прогона, фиксация результатов в памяти и при необходимости в репозитории |
| **ревизия и критика кода** | Цепочка «автор / один или несколько рецензентов»: риски, качество, соответствие целям; разные модели на разных этапах |

Ниже — как подключать **внешних и локальных** исполнителей на этих и других пайплайнах.

### Именованные пайплайны и подключаемые агенты

Любой пайплайн состоит из **этапов**; на каждом этапе может работать **свой исполнитель** — облачная модель, локальная или отдельный процесс («внешний агент»).

#### Три слоя (контекст ≠ исполнитель ≠ оркестрация)

1. **Контекст** — пресеты сборки из памяти ядра под задачу (research / experiment / code_review / chat).
2. **Исполнитель (Agent Backend)** — единый контракт: на входе уже собранные `messages` (+ опционально tools); на выходе текст или структурированный ответ этапа.
3. **Оркестрация** — линейная цепочка или DAG: например `draft → critique → synthesize`, где на `critique` назначен другой backend.

Локальная модель и «чужой» агент отличаются только реализацией backend’а, а не форматом пайплайна.

#### Контракт Agent Backend (цель реализации)

Идея интерфейса:

- **Вход:** сообщения (system/user/assistant/tool), опционально tools, лимиты по времени и токенам, ссылка на **имя профиля**.
- **Выход:** текст и/или JSON для этапов эксперимента или ревью.
- **Ошибки:** таймаут, rate limit → политика повтора или передача ошибки следующему этагу.

Реализации **v1** (минимум):

| Backend | Назначение |
|---------|------------|
| **OpenAI-compatible HTTP** | DeepSeek, OpenRouter, Groq, **Ollama**, **LM Studio**, **vLLM**, llama.cpp HTTP — всё с `/v1/chat/completions` |
| **Несколько профилей** | Разные `base_url` / `model` / ключи для «автора» и «критика» без ручной смены env между вызовами |

**Позже:** subprocess с JSON по stdin/stdout; при необходимости **MCP** для стандартного подключения удалённых агентов и инструментов.

#### Профили агентов (конфигурация)

Файл вроде `data/config/agents.yaml` (шаблон в репо можно, секреты — нет):

- Имена профилей: `primary`, `critic_local`, `research_cloud`, …
- Поля: `base_url`, `api_key_env` (**имя** переменной окружения, не значение), `model`, `timeout_sec`, опционально `max_tokens`.

Локальная модель задаётся профилем с `base_url: http://127.0.0.1:11434/v1` (типичный Ollama) и ключом по соглашению провайдера.

Код пайплайнов ссылается **только на имена профилей**.

#### Описание этапов пайплайна

- **v1:** кодовые пресеты в `cli/pipelines/*.py` — явная цепочка вызовов и привязка профилей к этапам.
- **v2:** декларативный YAML `{ stage, agent_profile, context_preset, prompt_template_id }` для добавления режимов без правки оркестратора.

Примеры цепочек:

- **Research:** контекст (episodic + external + цели) → generate (`research_cloud`) → опционально critique (`critic_local`) → запись эпизода.
- **Experiment:** черновик протокола → подтверждение пользователя → после прогона — разбор результатов тем же или другим профилем + теги в памяти.
- **Code review:** контекст с кодом и принципами из семантики → generate авторским профилем → один или несколько параллельных critique-профилей → synthesize.

Для нескольких рецензентов оркестратор ограничивает параллелизм и бюджет; слияние — отдельный этап.

#### Безопасность и стоимость

- Allowlist профилей или явный флаг CLI для вызова не-дефолтного endpoint.
- Лимиты числа этапов и ретраев на один запуск пайплайна.
- В логах никогда не печатать значения ключей.

**Этика, pulse, sleep** — трактовать как **отдельные пайплайны или этапы** после того, как базовые API памяти и один-два режима сборки контекста стабилизируются (не блокировать первый рабочий CLI).

### Data Flow

**Startup (нативный режим):**

1. `Memory(auto_boot=False)` (или эквивалент после рефактора).
2. Без неявного OpenCode; при необходимости пользователь: `import-opencode`.
3. Пайплайн boot (или лёгкий старт без полного boot): загрузка принципов, последних эпизодов, сессии CLI.
4. Создать/восстановить persistent CLI session.

**Per Turn:**

1. Ввод (текст или slash-команды: `/sleep`, `/screenshot URL`, `/boot`, `/exit`).
2. Сохранить ввод пользователя → рабочая память / общий лог (как договоримся в ядре).
3. **Пайплайн контекста** (`cli/context.py`): вызовы API памяти и вспомогательных инструментов под выбранный режим (chat / dev / …).
4. Multi-turn: LLM ↔ инструменты до финала.
5. Постобработка (в т.ч. при необходимости `Memory.respond()` — после согласования с планировщиком, чтобы не дублировать логику).
6. Сохранение: WM, эпизоды при чекпойнтах, CLI session.
7. Вывод + подсказки (pulse и т.д., когда подключены как пайплайн).

### CLI Commands

```
python eidos.py chat              # интерактивный диалог (пайплайн chat)
python eidos.py ask "..."         # одноразовый запрос
python eidos.py run research "..."   # именованный пайплайн (после реализации)
python eidos.py run experiment "..." # научно-инженерный протокол / журнал
python eidos.py review --paths FILE ... # ревизия кода (мультиагент по профилям)
python eidos.py boot              # показать / выполнить пайплайн boot
python eidos.py sleep --force     # ручной sleep
python eidos.py import-opencode   # импорт сессии из OpenCode в нашу память
```

## Key Decisions

1. **Пакет `cli/`**, не один файл.
2. **Runtime v1 — синхронный** (простой поток выполнения, без обязательного asyncio).  
   **План на потом:** перевести на **async** там, где это даёт выигрыш (параллельный I/O, стриминг, браузер, несколько источников памяти одновременно); блокирующие вызовы ядра при необходимости оборачивать в `asyncio.to_thread()` или выносить в пул.
3. **argparse + plain `input()`** для первой версии (без новых зависимостей для UX).
4. **Persistent session** — JSON в `data/cli_sessions/` (или слияние с WM после проектирования единого лога).
5. **LLM:** OpenAI-compatible HTTP; провайдер и ключ — конфиг + env (см. ниже).
6. **OpenCode:** только **импорт** истории, не обязательный источник правды при everyday chat.
7. **Browser:** опционально, по slash-команде или явному шагу пайплайна; политика безопасности для URL (SSRФ) — отдельно.
8. **Sleep:** порог по событиям (например 50, как сейчас `WM.AUTO_SLEEP_THRESHOLD`) и/или `/sleep`.
9. **Planner:** стратегии respond / verify / search / sleep / goal — согласовать момент вызова с `Memory.respond()`, чтобы не планировать дважды без нужды.

## Секреты и конфигурация

### Базовый вариант (наш дефолт)

- **`DEEPSEEK_API_KEY`** (или универсально **`LLM_API_KEY`**) в переменных окружения.
- Опционально: **`LLM_BASE_URL`**, **`LLM_MODEL`** — чтобы не пришить всё к одному провайдеру.

### Как делают в других CLI и инструментах (для ориентира)

| Подход | Где встречается | Комментарий |
|--------|-----------------|-------------|
| Env vars (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, …) | OpenAI/Anthropic SDK, большинство обёрток | Простой стандарт для CI и серверов |
| Файл `.env` в проекте (не в git) + загрузка при старте | Many Node/Python CLIs, `aider`, локальная разработка | Удобно для одного репозитория; риск случайного коммита — только с `.gitignore` |
| Глобальный конфиг в `~/.config/<app>/` или `~/.<app>/` | `git`, многие Linux CLI | Переносимость между проектами |
| Профили как у AWS (`~/.aws/credentials`, `AWS_PROFILE`) | boto, aws-cli | Несколько аккаунтов/ролей без смены env вручную |
| Интерактивный login + токен в keychain/credential store | `gh auth login`, некоторые IDE-интеграции | UX лучше для людей; сложнее для headless |
| Менеджеры секретов: **1Password** (`op run`), **Vault**, облачные secret managers | Команды в командных Makefile/CI | Централизованная ротация, аудит |
| **`direnv`** | Пер-проектные env при `cd` в каталог | Удобно в монорепах |
| Прокси-ключ один раз (**LiteLLM**, корпоративный gateway) | Организации | Клиент хранит только URL прокси и короткоживущий токен |

Практичная политика для Эйдоса v1: env как источник правды + документированный опциональный `.env` (через `python-dotenv` только если добавите зависимость) или shell-обёртка; профили (`EIDOS_PROFILE` / файл конфига) можно добавить, когда появится несколько моделей/ключей.

## Будущее: публичная летопись (GitHub)

Цель: агент ведёт **открытый хронологический текст** (блог, заметки, отчёты по экспериментам), отделённый или связанный с приватным репозиторием Logos.

**Варианты технически:**

| Вариант | Плюсы | Минусы |
|---------|--------|--------|
| Отдельный репозиторий `eidos-log` / `blog`: только Markdown + статический генератор (MkDocs, Hugo, Jekyll) + **GitHub Pages** | Простой деплой, история в git, PR как ревью черновиков | Два репо; нужен PAT/`gh` для пуша из агента |
| Ветка или каталог внутри Logos (`docs/blog/` или `public/`) | Один клон, связь с кодом и памятью | Смешение публичного и приватного — нужна дисциплина и `.gitignore` |
| Автокоммиты из CLI по команде `/publish` или по расписанию | Явное действие, аудит в истории | Риск «шума» в коммитах без политики |

**Смысловая связь с памятью:** публикация не заменяет эпизодическую память — это **выжимка или редакция** (принципы из `BOOK.md`, итог сессии, гипотеза эксперимента). Источник правды для рассуждений остаётся в ядре; блог — для людей и для непрерывности «лица» проекта снаружи.

**Инструменты:** `git`, при необходимости **GitHub CLI** (`gh`), токен с минимальными правами на один репозиторий; опционально GitHub Actions только для сборки сайта, без хранения секретов LLM в репо.

## Будущее: электронная почта

Цель: свой адрес (или алиас), **приём**, **ответ**, **произвольная обработка** писем как входящего сигнала в пайплайн памяти.

**Компоненты:**

- **Отправка:** SMTP провайдера или HTTP API (Resend, SendGrid, Mailgun, SES). Проще и безопаснее начать с API + ограниченный «разрешённый список» получателей на первых порах.
- **Приём:** IMAP polling; или **входящий webhook** у провайдера (если есть); или пересылка на скрипт/Inbound Parse — зависит от хостинга почты.
- **Обработка:** нормализация в текст + вложения (осторожно с размером и malware) → запись в эпизодическую память / external → опционально ответ через LLM → очередь «human approval» для чувствительных действий.

**Риски (обязательно проектировать заранее):**

- Спам, фишинг, социальная инженерия к агенту.
- Утечки секретов из цитируемых писем в публичный блог или в git.
- Юридические аспекты (GDPR, хранение переписки) при работе с данными третьих лиц.

**Архитектурно:** почта — это **ещё один транспорт**, как CLI: те же пайплайны этики и политики инструментов, отдельный модуль `kernel/mail/` или внешний микросервис с явным контрактом; не смешивать с основным циклом чата без очереди и лимитов.

Почта и блог логично включать **после** стабильного CLI и явных API памяти — иначе сложно контролировать, что именно уходит наружу и что попадает в летопись.

## Репозиторий: структура, слои, зависимости

Ниже — карта «что где лежит» и **кто от кого зависит** в коде и в пакетах. Удобно стыковать с будущим `cli/` и рефактором памяти.

### Каталоги (физическая структура)

| Путь | Роль |
|------|------|
| `kernel/` | Ядро: память, boot, планировщик, этика, журнал, внешняя память, цели, dashboard logic, браузер, OpenCode-адаптер |
| `body/` | Оболочка развёртывания: `requirements.txt`, `bootstrap.sh`, `sleep.sh`, хуки |
| `data/` | Рантайм-данные (часто в `.gitignore`): working, episodic, semantic, journal, external, planner, … Пути в `kernel/config.py` |
| `tests/` | Pytest по ядру |
| `experiments/` | Изолированные гипотезы + частично legacy-import через `sys.path` из `kernel/memory.py` (budget, verifier) |
| `dashboard/` | Отдельное приложение Streamlit поверх `kernel.dashboard` |
| `rubert-tiny2/`, `all-MiniLM-L6-v2/` | Локальные веса эмбеддеров (не Python-пакеты) |

Планируемый **`cli/`** + **`eidos.py`** в корне — новый слой **над** `kernel`, без циклических импортов внутрь себя.

### Внутренний граф ядра (упрощённо)

```
kernel/config.py          ← только stdlib (paths)
kernel/utils.py, compress.py, salience.py
kernel/planner.py         ← config + файлы outcomes
kernel/opencode_adapter.py ← stdlib + SQLite путь ~/.local/.../opencode.db
kernel/instrumental.py    ← config
kernel/goals.py           ← config
kernel/ethics.py          ← config
kernel/health.py          ← config

kernel/memory.py          ← ЦЕНТР: WorkingMemory, EpisodicMemory, SemanticMemory, Memory
                              ├→ config, utils (atomic_write)
                              ├→ goals (прямой импорт)
                              ├→ лениво: external.ExternalMemory, journal.Journal
                              ├→ sleep → compress, salience; ethics через record_episode
                              └→ assess_complexity / verify: experiments на sys.path

kernel/boot.py            ← boot_context(memory); опционально OpenCodeAdapter внутри

kernel/agent_pulse.py     ← Memory (типичный паттерн «обёртка над Memory»)
kernel/mission_control.py ← Memory + config

kernel/external.py        ← numpy + transformers + torch (ленивая загрузка модели)
kernel/journal.py         ← то же для векторного поиска по дневнику
kernel/browser.py         ← playwright

kernel/dashboard.py       ← health + instrumental + DB reads
```

**Правило для нового кода:** фичи, которые не должны тянуть ML или браузер при старте CLI, вызывать **через ленивые методы** как у `Memory.external()`, либо выносить в отдельные подпакеты с опциональными extras.

### Внешние зависимости (факт по импортам)

| Уровень | Пакеты | Где используется |
|---------|--------|-------------------|
| **Минимум (stdlib)** | — | `config`, большая часть `memory`, `boot`, `ethics`, `goals`, `planner`, `instrumental`, `health`, `opencode_adapter` |
| **ML / векторы** | `numpy`, `torch`, `transformers` | `external.py`, `journal.py` (ленивая загрузка `rubert-tiny2`) |
| **Браузер** | `playwright` | `browser.py` |
| **UI** | `streamlit` | `dashboard/app.py` |
| **Тесты** | `pytest` | `tests/` |

Файл `body/requirements.txt` указывает на каталог **`requirements/`**: профили `kernel-min`, `kernel-ml`, `cli`, `dev`, `full-local` и т.д. (см. `requirements/README.md`).

### Эксперименты и динамический `sys.path`

`Memory.assess_complexity` и верификация подмешивают в `sys.path` каталоги `experiments/002-*` и `003-*`. Это **скрытая связность**: будущий CLI либо переносит эти модули в `kernel/`, либо регистрирует их как явные плагины с интерфейсом.

### Зависимости будущего `cli/` (целевые)

| Зависимость | Для чего |
|-------------|----------|
| `kernel.*` | Память, boot-пайплайн, инструменты, при необходимости planner/ethics |
| HTTP-клиент | Вызов OpenAI-compatible API (`urllib` достаточно для минимализма; `httpx` удобнее для стриминга позже) |
| Опционально | `python-dotenv` для `.env`; позже async-библиотека если перейдёте на asyncio |

CLI **не должен** импортировать `dashboard/` и по умолчанию — не импортировать `playwright` / `transformers`, пока пользователь не включил соответствующий инструмент.

### Диаграмма слоёв (кто кого может звать)

```
┌─────────────────────────────────────────────────────────┐
│  transports: cli/ (будущее), dashboard/, body/*.sh    │
└───────────────────────────┬─────────────────────────────┘
                            │ импорт
┌───────────────────────────▼─────────────────────────────┐
│  kernel/  — когнитика, память, политики                  │
│  (избегать обратных импортов из kernel в cli)           │
└───────────────────────────┬─────────────────────────────┘
                            │ файлы / SQLite
┌───────────────────────────▼─────────────────────────────┐
│  data/  +  BOOK.md / JOURNAL.md (текстовые носители)    │
└─────────────────────────────────────────────────────────┘
```

Итого: **единственный «тяжёлый хаб» — `Memory` и `config`;** ML и браузер — краевые опциональные модули; **CLI** — тонкий транспорт и пайплайны поверх стабильных API памяти (после рефактора — явные интерфейсы видов памяти).
